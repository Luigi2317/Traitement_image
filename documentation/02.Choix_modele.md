# 02. Choix du modèle

## 2.1 Choix du modèle

### Approche

Les 4 modèles candidats sont entraînés **1 epoch** (les détails seront donnés plus bas) sur le split train (6 479 images) et évalués sur le split val (1 458 images). Le choix est fondé sur les métriques réelles obtenues, confrontées aux contraintes du projet.

### Contraintes du projet

| Contrainte | Valeur |
|---|---|
| Images d'entraînement | 6 479 |
| Petites boîtes (aire < 1%) | 52.3% |
| Déséquilibre entre classes | ratio 118.9x |
| GPU disponible | Standard (~8 GB VRAM) |

---

### Les 4 modèles candidats

**YOLOv8m** — Détecteur mono-passage. Analyse l'image en une seule passe via une grille. Résolution d'entrée configurable (640px pour la comparaison). 25.9M paramètres.

**Faster R-CNN (ResNet50-FPN)** — Détecteur deux étapes. Un premier réseau (RPN) propose des zones candidates, un second les classe. Backbone ResNet50 avec Feature Pyramid Network pour les petits objets.

**SSD300 (VGG16)** — Détecteur mono-passage. Résolution fixe à 300×300. Backbone VGG16. Architecture de 2016, moins récente que YOLO.

**DETR (ResNet50)** — Détecteur par transformeur. Analyse l'image globalement via un mécanisme d'attention, sans ancres ni grille. Nécessite de nombreuses epochs pour converger.

---

### Résultats de la comparaison (1 epoch, split val — 1 458 images)

L'objectif initial était d'entraîner chaque modèle 10 epochs. En pratique, l'entraînement s'est déroulé sur un serveur distant (Scaleway, Tesla P100 16 GB) via une connexion Jupyter, et plusieurs incidents ont interrompu les sessions : coupures WiFi, mise en veille du poste local entraînant la perte du kernel, et noyaux Jupyter trop chargés monopolisant la VRAM. Ces interruptions répétées ont conduit à limiter l'entraînement à **1 epoch par modèle** pour garantir que chaque modèle termine dans une session stable. En effet les durées du Faster R-CNN , du DETR et du SSD300 prenait plus de 100 min pour 2 à 3 epochs seulement. Donc dès qu'un souci arrivait, tout relancer prenait le même temps.

Cette durée réduite est suffisante pour comparer les architectures entre elles (les tendances relatives restent valides), mais ne correspond pas à la convergence finale — les valeurs absolues de mAP50 sont donc inférieures à celles obtenues après entraînement complet (voir doc 04 pour YOLOv8m entraîné 100 epochs).

| Modèle | mAP50 (%) | Inférence (ms/img) | GPU (GB) | Durée entraînement (min) |
|---|---|---|---|---|
| Faster R-CNN | 43.1 | 91.3 | 6.5 | 64.8 |
| YOLOv8m | 41.5 | 244.8 | 6.4 | 6.9 |
| SSD300 | 19.4 | 17.9 | 2.5 | 48.9 |
| DETR | 0.0 | 50.6 | 3.3 | 86.6 |

**Note sur DETR** : le score mAP50=0.0 après 1 epoch est attendu. DETR est une architecture à transformeurs qui nécessite plusieurs dizaines d'epochs pour que le mécanisme d'attention converge — avec une seule epoch, le modèle n'a pas encore appris à associer les requêtes d'objets aux régions de l'image. Ce comportement est documenté dans le papier original (Carion et al., 2020).

---

### Modèle retenu

**Modèle retenu : YOLOv8m**

Faster R-CNN obtient un mAP50 légèrement supérieur (+1.6 points) à 1 epoch, mais YOLOv8m est retenu pour les raisons suivantes :

- **Temps d'entraînement** : 6.9 min contre 64.8 min pour Faster R-CNN — un facteur 9x, décisif pour itérer rapidement sur les hyperparamètres et la résolution d'entrée ;
- **Architecture adaptée aux petits objets** : YOLOv8m intègre nativement un Feature Pyramid Network (FPN) et est conçu pour la détection multi-échelle, ce qui correspond au profil du dataset (52% de petites boîtes) ;
- **Écart de mAP50 à 1 epoch non représentatif** : après entraînement complet (100 epochs, voir doc 04), YOLOv8m atteint mAP50=0.651, performance cohérente avec l'état de l'art sur des datasets similaires.

Il sera configuré et entraîné complètement en section 2.2.

---

### Choix du variant : pourquoi YOLOv8m et pas un autre

YOLOv8 existe en plusieurs tailles (n, s, m, l, x). Le choix du variant **medium (25.9M paramètres)** s'appuie sur les contraintes du dataset :

| Variant | Paramètres | Décision |
|---|---|---|
| YOLOv8n / s | 3–11M | Trop petit pour 17 classes avec 52% de petits objets |
| **YOLOv8m** | **25.9M** | **Retenu — bon compromis précision / vitesse / overfitting** |
| YOLOv8l / x | 44–68M | Surdimensionné pour 6 479 images d'entraînement |

**Pourquoi pas YOLOv8n / s (3–11M) :** avec 17 classes dont 52.3% de petites boîtes et un déséquilibre de classe de 118.9x (`hands` vs `face-guard`), ces variants ont une capacité trop limitée pour bien apprendre les classes rares en plus des classes fréquentes — au détriment de `face-guard`, `ear-mufs`, etc.

**Pourquoi pas YOLOv8l / x (44–68M) :** avec seulement 6 479 images d'entraînement et `freeze=10` (backbone gelé, voir 2.2), un modèle à 44-68M de paramètres a beaucoup plus de capacité que nécessaire pour ce volume de données — risque de mémoriser les images d'entraînement plutôt que de généraliser (overfitting). De plus, sur le P100 (16 Go), un modèle plus gros impose soit un `batch` plus petit (entraînement plus lent), soit moins de marge pour augmenter `imgsz` par la suite — ce qui s'est avéré déterminant pour le passage à 1024×1024 (voir doc 04, section 2.4).

YOLOv8m est donc le compromis : assez de capacité pour 17 classes + petits objets, sans être surdimensionné par rapport aux 6 479 images disponibles.

*Note : la comparaison ne porte que sur les variantes YOLOv8 (la version dont les poids COCO `yolov8m.pt` sont utilisés ci-dessus) — les versions plus récentes (YOLOv9/v10/v11) ne font pas partie des architectures comparées, qui se limitent aux 4 familles demandées par la consigne (YOLO, Faster R-CNN, DETR, SSD).*

**Pourquoi YOLOv8 plutôt que des versions plus récentes (v9/v10/v11) :** d'après nos recherches, YOLOv8 est la version la plus solide pour démarrer un projet — c'est la plus documentée, avec le plus de tutoriels, d'exemples et de retours d'expérience disponibles. Les versions plus récentes promettent des gains marginaux sur des benchmarks comme COCO, mais avec moins de documentation et de retours pour anticiper les problèmes rencontrés en pratique (ex. les instabilités d'entraînement déjà observées avec DETR sur ce projet).
